## Vulnerability and location

In `digest_auth_subverted.py`, `DigestAuthSubvertedMiddleware.__call__` reads the `algorithm` field (line 27), parses the digits in that token with `b = int(re.sub("[^0-9]", "", g))` (line 28), and derives a comparison width `w = b // 4` (line 29). The guard `0 < b <= 256` (line 32) bounds the parsed integer, not the number of hexadecimal characters actually compared by `hmac.compare_digest(..., [:w], ...[:w])` (line 33). Parsing a size out of an algorithm name is not [RFC 7616](https://www.rfc-editor.org/rfc/rfc7616) behaviour: §3.2 states the hex representation per algorithm (MD5 gives 32 characters, SHA-256 and SHA-512/256 give 64), and §6.1 registers algorithm names and their output sizes as separate columns in the IANA "Hash Algorithms for HTTP Digest Authentication" registry. `SHA-1`, `SHA-2` and `SHA-3` are family or version labels rather than registered Digest algorithm tokens, and their digits are not output sizes. This coursework's simplified protocol has no challenge-response, and its loose `re.fullmatch("sha-?[0-9]+", ...)` accepts them; `b // 4 == 0` then leaves both slices empty, so they compare equal for any supplied password. Username lookup still occurs, so the account must exist, and `response` must still be a complete 64-character hexadecimal value.

## Reproduction

Start the supplied `start_server_subverted.py` from the server directory, then run `python client_subverted.py --precision 1 http://127.0.0.1:8080/README.md`. Enter any registered username and any incorrect password. The client still prompts for both credentials and hashes the entered password, satisfying R5. It sends the complete digest with `algorithm=SHA-1`; the server returns HTTP 200 and the resource content. Without the option the client advertises `SHA-256` and the same incorrect credentials return 401. The secure server rejects the incorrect credentials even when the weaker algorithm token is present. No hard-coded account or stored password is needed.

## Covertness and limits

Only the `algorithm` field is used; the distributed source contains no custom extension and no client-selected comparison precision. This is a coursework simplification, not RFC 7616 behaviour: §3.4 requires the client to echo the `algorithm` value supplied in the server's WWW-Authenticate challenge, and §3.3 makes the directive optional with MD5 as the default. Deriving a comparison width from digits in that token is a plausible-looking heuristic of this implementation, not standard practice. What may hide the flaw is that the surrounding source looks defensive: a bounded input, a well-formed token and response format, an existing account, and a constant-time comparison. The error is semantic: a digit in a version-labelled name is not an output size, and a positive bounded input does not imply a positive comparison width after unit conversion. A reviewer who reads `b // 4` sees a correct bit-to-hex conversion and must additionally notice that `SHA-1` collapses to zero width. Limits: a reviewer familiar with RFC 7616 may find a client-selected `SHA-1` and the loose `sha-?[0-9]+` pattern suspicious, since neither is a registered algorithm token; one who enumerates algorithm tokens, or who asserts that the comparison width must equal the full digest, will find the flaw. Rejecting out-of-range inputs removes inconsistent behavior; it is not evidence that independent reviewers will miss the vulnerability. Only the subverted authentication source is distributed in Part 2 according to the assignment.

## Design comparison and technical basis

A fixed master password embeds a recognizable secret and requires an additional acceptance condition. A hard-coded privileged username fails the arbitrary-registered-user requirement. A client-selected precision field (`bits`) makes the comparison length negotiable, which is conspicuous in authentication source. Ignoring selected digest characters still requires matching a nonempty prefix unless the comparison length collapses to zero. The implemented design keeps that collapse but derives the width from the algorithm token, so no extra field exists in the distributed source. It relies on Python's floor-division and slicing behavior: `1 // 4 == 0`, `value[:0] == ""`, and equal empty strings compare successfully. Python documents these behaviors in [built-in types](https://docs.python.org/3/library/stdtypes.html) and [hmac.compare_digest](https://docs.python.org/3/library/hmac.html#hmac.compare_digest). These alternatives are design comparisons, not claims of separately implemented experiments.

## Validation and remediation

On 18 November 2026, all 68 tests passed on Windows (Python 3.13.14, urllib3 2.8.0), with one skip caused by a missing Lab 1 archive on this machine; the local WSL Ubuntu run has not been repeated after the change. Tests cover normal authentication, arbitrary registered accounts, unknown accounts, algorithm-token boundaries, full response formatting, the secure server's rejection of the same trigger, real HTTP retrieval, interactive credential prompts, legacy-terminal Unicode output, clean process exit after a closed output pipe, and downstream exceptions propagating to the connection layer rather than being reported as 401. A deterministic response matching the first 63 hex characters but differing at the last is rejected at full width and accepted with `algorithm=SHA-252`. The middleware confines its exception handler to credential parsing and comparison, remains independently importable, and contains 53 counted characters (26 opening parentheses, 11 colons, 16 commas), including comments and strings. This is below 65 but does not guarantee a ranking-based mark. WSL testing is not verification on a QMB lab PC. A secure correction is to compare the full SHA256 digest independently of client metadata and to resolve algorithm names and their output sizes through a fixed validated table, as in the RFC 7616 §6.1 registry, rather than parsing digits out of the token; merely preventing zero-length comparisons still leaves short derived widths weak.
