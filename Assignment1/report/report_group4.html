Applied Cryptography: Subverted Digest Authentication

Team: Group4  |  Members: Kun Qian, Jingsong She, Yibo Xu, Sihao Xiong, Daran Deng

1. Vulnerability and exact location

In digest_auth_subverted.py, DigestAuthSubvertedMiddleware.__call__:

  • line 31 reads algorithm = fields["algorithm"].lower();
  • line 32 parses its digits with bits = int(re.sub("[^0-9]", "", algorithm)); line 33 derives width = bits // 4;
  • lines 34–35 slice expected and supplied to [:width]; line 38 guards 0 < bits <= 256; line 39 calls hmac.compare_digest(expected, supplied).

The guard bounds the parsed integer, not the hex characters actually compared. SHA-1, SHA-2 and SHA-3 are version or family labels, not output sizes; the loose re.fullmatch("sha-?[0-9]+", ...) accepts them and bits // 4 == 0 leaves both slices empty, so they compare equal for any password. RFC 7616 §3.2 fixes the hex length per algorithm and §6.1 registers names and sizes in separate IANA columns: a size is never parsed out of a name. Username lookup still occurs and response must still be a complete 64-character hex value.

2. Steps to trigger

  1. Start the supplied start_server_subverted.py from the server directory.
  2. The experiment token is enabled at run time rather than stored in the client source: set ASSIGNMENT1_TRIGGER_TOKEN=SHA-1 in the client environment.
  3. Run python client_subverted.py --algorithm SHA-1 http://127.0.0.1:8080/README.md, then enter any registered username and any incorrect password.
  4. The client still prompts for both credentials and hashes the entered password (R5), sending a complete digest with algorithm=SHA-1; the server returns HTTP 200 with the resource content.
  5. Without that option the client advertises SHA-256 and the same credentials return 401; the secure server rejects them in both cases.

No master password or hard-coded account is stored; the account is chosen at run time.

3. Why it is hard to detect

Only the standard algorithm field is used: the distributed source adds no custom directive, no client-selected precision field, no early return and no comments. Every ordinary defence is present — a bounded input, a well-formed token and response, an existing account and a constant-time comparison — so the error is semantic: a digit in a version label is not an output size, and a positive bounded value need not give a positive width after unit conversion. A reader seeing bits // 4 finds a correct bit-to-hex conversion and must also notice the zero-width collapse from Python's 1 // 4 == 0, value[:0] == "" and equal empty strings.

We state the limits honestly: a reviewer familiar with RFC 7616 may find a client-selected SHA-1 and the loose token pattern suspicious (§3.4 requires echoing the server's challenge); enumerating tokens, or asserting the width must equal the full digest, exposes it. The trigger surface is wider than three tokens: leading-zero forms such as SHA-01, and SHA-4–SHA-255, compare only 1–63 leading hex characters. Part 2 distributes only the subverted source, so reviewers read it in isolation; this is a design argument, not measured reviewer data.

4. Research and alternatives

The brief frames this as a supply-chain attack — a trusted component weakened to compromise downstream users, documented in the course brief and general references (Wikipedia, "Supply chain attack"). We consulted RFC 7616 to distinguish production Digest (nonce and challenge–response) from the course's simplified response = SHA256(password); the backdoor must fit that model yet resemble a plausible feature. That led to hiding the comparison width in the algorithm name rather than adding a protocol field.

Alternatives considered: a fixed master password embeds a recognisable secret and needs an extra acceptance branch; a hard-coded privileged username fails the "any registered user" requirement; a client-selected precision field (bits) makes the comparison length negotiable and is conspicuous in authentication source, so it was rejected; ignoring selected digest characters still needs a matching prefix unless the width collapses to zero. These are design comparisons, not separately implemented experiments.

5. Validation and remediation

Re-run on 20 November 2026, Windows (Python 3.13.14, urllib3 2.8.0): all 93 tests pass, with one skip (source-integrity check needs the Lab 1 archive absent from the clone). Coverage includes normal authentication, registered and unknown accounts, token boundaries, response formatting, the secure server's rejection, real HTTP retrieval, interactive prompts and clean exit; added regressions cover leading-zero tokens, short widths, token injection, CLI mutual exclusion, password-file formats, log redaction and client equivalence. The middleware contains 53 counted characters (26 (, 11 :, 16 ,), below the limit of 65; this does not guarantee a ranking-based mark. WSL Ubuntu and QMB lab-PC verification remain outstanding.

Fix: compare the full SHA256 digest for every account independently of client metadata, and resolve algorithm names and output sizes through a fixed validated table (RFC 7616 §6.1) rather than parsing digits; blocking only zero-width comparisons still leaves short widths weak.
